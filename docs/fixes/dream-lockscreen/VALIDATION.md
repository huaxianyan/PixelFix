> 本文件自本地 Android 问题工作区迁移，记录的是迁移前「屏保锁屏修复」独立模块时期的调查与验收。文中的本地目录（`.work/...`）与旧包名属于迁移前状态，现包名为 `com.neko7ina.pixelfix`，版本见 [开发进度](../../STATUS.md)。

已完成独立模块 `0.1.0`，本地编译、1 条选择条件单元测试和 APK 签名检查通过。产物和操作清单见 [构建与待测安装包](BUILD.md)。测试 APK 已经用户当次授权安装，用户自行启用并重启。设备加载、主线程命中和一次宽限清理已确认，但随后仍出现人脸成功、锁头关闭、上滑要求 PIN。`0.1.0` 未通过完整现场验收，不能继续按已修复处理。保留现场与下一处断点见 [调查记录](INVESTIGATION.md)。

本地开发阶段遵照用户要求未操作手机。设备连接后，用户仅授权助手安装应用，启用、作用域和重启由用户自行处理。重启和复现后，助手只读保存日志与 PIN 界面状态，没有输入凭据或再次改变设备状态。

随后构建并经当次授权覆盖安装 `0.2.0`，用户自行重启。构建、2 条条件测试和签名检查通过。设备确认新版本、两个所有者捕获，以及屏保开始时的主线程重置。

用户报告尝试数次未再触发，准确次数未知。日志确认旧模型从 NONE_UNLOCKED / FACE_SENSOR 变为 NONE / null，随后重新锁定、真实人脸成功、设备进入状态恢复已解锁，用户操作进入桌面。本轮复测通过，长期复现率尚无结论。

代表时序为 11:53:11.461 模式重置、12.465 重锁、14.093 人脸成功、14.097 恢复解锁和 17.435 进入桌面。证据为 `.work/dream-lockscreen/0.2.0-first-test-module.txt` 与 `0.2.0-first-test-buffers.txt`。日志中的 7 次模式重置、4 次宽限清理不是完整测试次数。

条件单元测试只证明选择范围，以上运行时结论来自设备日志。下方完整回归表仍未逐项验收，尤其是独立的主动锁定、指纹与 PIN 路径。当前先保持用户日常使用状态观察，不为补数字强行反复测试。

## 现场验收

| 用户操作 | 预期可见结果与证据 |
| --- | --- |
| 进入时钟屏保，在宽限期内双击退出并完成人脸认证 | 按现有设置进入锁屏或桌面，原屏保闹钟不再打断已完成的新流程 |
| 人脸认证设置为仍需操作才能进入设备 | 人脸成功后继续显示锁屏，用户操作后进入桌面 |
| 留在屏保直到锁定宽限期到期 | 设备按原策略锁定，退出屏保后正常认证 |
| 从锁屏通过指纹进入 | 指纹正常认证并进入设备，窗口和场景状态一致 |
| 按电源键主动锁定，再唤醒 | 保留原锁定策略，认证完成前受锁屏保护 |
| 普通熄屏与唤醒，不进入时钟屏保 | 行为与补丁停用时一致 |

原故障低频，未出现一次不能证明修复。每轮记录实际次数、操作差异和结果，不预设一个没有依据的「充分次数」。优先验证失败时序中的许可与旧计时已按预期结束，而非仅观察桌面是否闪现。

首轮先确认模块日志包含适配、Hook 安装和计时所有者捕获。命中原生屏保退出锁屏分支时，应记录 `hit:`，随后报告 INACTIVE、许可 false 和闹钟序号递增一次。还须观察旧截止时刻之后的原生日志，确认许可未重新开启、旧闹钟未改变当前流程。错误线程或所有者缺失会停止本进程的修复，不能把此类跳过当作验收通过。

本地单元测试只覆盖 6 种请求的选择条件。它没有模拟认证、协程传播或闹钟执行，也不是走真实设备入口的端到端测试。端到端证据由本表中的真机操作补齐。

后续补充验收必须覆盖：人脸通过但尚未上滑时再次进入屏保，退出后重新完成人脸识别，再上滑进入设备。需要同时确认锁头、密码面板、设备进入状态和指纹监听，不能只检查第一轮退出或只检查旧宽限闹钟。

## 部署与回退

- 安装和启用仅限用户当次授权，保留同一签名身份，使用覆盖安装。
- 日志区分适配成功、Hook 安装成功、实际命中与处理结果，编译成功单独记录。
- 如发生异常，先保留日志，再经用户确认关闭本修复并重启。不修改认证数据来恢复现场。
- 用户已自行恢复模块并重启，实际启用清单待核对。对照实验前的原启用清单在本地取证目录，不能当作当前状态。后续测试不得顺手改变其他模块或作用域。

## 系统更新后的处理

系统构建变化后，旧修复保持停用。先在停用状态下核对原生实现和原故障，再决定重新适配。若系统已修复，就退役本补丁，保留结论与回退记录，无需发布。
